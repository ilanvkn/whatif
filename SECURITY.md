# Security scope

The original smoke runner remains bounded, GET-only and literal-loopback-only. V1.1 campaigns add reviewed browser requests, k6 GET load and synthetic-account security checks against literal loopback HTTP(S) or authorized HTTPS staging. Exact target acknowledgement is an execution guard, not proof of ownership or user authorization. The host must establish matching target, action and budget scope.

Campaigns do not evaluate arbitrary scenario JavaScript or shell text. Engine executable/module paths come from the operator's local configuration and must be trusted separately. Each browser uses an isolated profile. Only declared same-origin method/path pairs are allowed; query strings can vary. Redirects, service workers, WebSockets and downloads are unsupported. A discovered redirect bypass was fixed and regression-tested. Browser-local interventions do not alter the server, but ordinary allowed form/API requests can mutate application state. Use disposable records and application-specific cleanup.

Request/VU/duration ceilings and owned process-group deadlines bound execution. SIGINT/SIGTERM stop the current worker and its owned descendants on the qualified macOS path. Windows process-tree cancellation is unqualified. Engine crashes or interruption can leave request counts unknown; directories cannot be silently replayed. These controls are not an operating-system network sandbox or defense against a malicious engine binary.

Security checks use synthetic bearer credentials referenced through WHATIF_* environment variables. Bodies are inspected only in bounded memory, and credentials, DOM, screenshots, headers and bodies are not persisted by these adapters. Campaign JSON and generated scripts can contain operator-entered values, so never put real secrets in literal fields. Source leads and status checks are not comprehensive vulnerability verdicts. A failed owner positive control is inconclusive.

Paths, fixture markers, statuses, questions and hashes can still reveal project information. Keep evidence project-owned. Hash indexes detect byte changes but are not signatures: someone who rewrites artifacts and the index can rewrite the hashes too. No production capacity, full exploit resistance or trusted attestation follows from a passing run.

No cloud output, arbitrary attack payloads, persistence or real-data exfiltration are enabled. Semgrep/ZAP and distributed engines remain separate future integrations. Until a public repository contact is configured, report issues privately to the owner rather than publishing credentials or exploit details.
