# V3 real application workflow

The public surfaces are MCP, CLI and a local Node JavaScript API. No HTTP API service is started by importing the module. The host supplies current task authorization; a matching source acknowledgement is a guard, not proof of ownership.

1. Choose an owned checkout and record exact upstream Git identity and license. Use `scripts/prepare-real-app.mjs` for the pinned TodoMVC and Markdown examples; it checks selected files against committed blobs and executes no install hooks. Read `docs/REAL-APP-PREPARATION.md` at the plugin root.
2. Review an app manifest: schemaVersion3, runner static-web, exact source directory, served asset list, reviewed source files, editable subset, entry HTML, repeat safety, provenance, application contract, campaign oracles, operators and cumulative budgets. No blanket directory packaging. Assets are at most100 files,4MiB each and16MiB total. Reviewed source remains separately bounded.
3. `whatif_app_plan({manifest,out})` / `app-plan --manifest FILE --out NEW_DIR` pins asset hashes without inference or app traffic. Then inspect team.json. Source changes after planning require a new plan.
4. `whatif_team_run({teamDirectory,ackSource})` / `team-run --team DIR --ack-source EXACT_CANONICAL_SOURCE` copies assets, starts a trusted read-only static host, runs real browser cases, asks independent critics, applies allowlisted model patches and replays the exact cases. All declared baseline cases remain mandatory. The original checkout is unchanged. Accepted fixes are committed only in the isolated copy; rejected or unapproved fixes roll back.
5. Verify from a fresh process with `whatif_team_verify` / `team-verify --team DIR`. Source identity covers reviewed files, while every additional asset stays pinned. The verifier reconstructs permitted cases from the manifest, rather than trusting hashes alone. An incomplete interrupted ledger cannot become a complete result.
6. `whatif_qualify({teamDirectories:[...],out})` / `qualify --teams ABS_DIR_1,ABS_DIR_2 --out NEW_DIR` creates a retrospective report with usage, exact case transitions and evidence-bound observations. Complete cross-application qualification requires two distinct upstream repositories, real-provider receipts and completed runs. This is finite qualification of those cases, not product-wide certification.

Browser actions include reviewed navigation, click/double-click, fill, allowlisted keys, reload, visibility/text/value/count/attribute assertions and synthetic initial localStorage. Only exact reviewed same-origin requests run. Optional localMirrors map specific HTTPS GET URLs to pinned local paths; they do not authorize outgoing traffic and are recorded as substitutions. Every mirror path must be in the local request allowlist. Keep real credentials out of synthetic storage and scenario files.

macOS Seatbelt plus Node permissions isolate the static host. Browser contexts are disposable; the adapter never imports the upstream JavaScript into the controller. Source disclosures use existing Codex authentication. Separate sessions may use the same model weights. Call/time/request/input/output limits apply; reported tokens are checked between calls, not hard token/dollar caps. No automatic mid-run resume or endless successor runs.

Supported runners cover real client applications and explicitly prepared Python/SQLite/PostgreSQL backends on macOS. Unreviewed database engines, build hooks, OAuth, native/mobile runtimes and distributed load need separate reviewed adapters and evidence. Never generalize two successful apps to “anywhere, anything,” or to comparative superiority.

## Python/SQLite/PostgreSQL backends

Use `runner: python-sqlite` with a reviewed immutable bootstrap, exact asset list and an absolute reviewed Python environment. Planning fingerprints the interpreter and runtime trees. No dependency installation is performed by team-run. See `examples/backends` and the backend preparation script.

The `api` campaign engine executes allowlisted same-origin methods, synthetic registration/login, captured bearer tokens and JSON-pointer assertions. Tokens, cookies and response bodies are not persisted. Use synthetic credentials only. Each repeated confirmation begins from the identical empty database seed. After the main campaign, WhatIF stops the owned server, restarts it against the same database and runs the immutable restart campaign. Both campaigns must pass for acceptance.

macOS isolation restricts writes to private database storage, denies outgoing connections and child processes, and restricts the listener to its assigned loopback port. The runner checks SQLite integrity and records table counts and file hashes, then removes private databases and generated session secrets. Verification checks reset/restart/process/runtime evidence and cleanup. The historical SQLite evidence remains limited to its declared trials. PostgreSQL workflows require a pinned PostgreSQL 17 runtime, a disposable Unix-socket cluster, a restricted application role, cold-seed reset proof and cluster/socket cleanup. Declared background workers require separate launch/source/runtime/stop receipts; completion must be asserted through the API. Neither worker startup nor client request overlap establishes successful job processing or simultaneous database transactions. OAuth and production capacity remain unqualified.

Keep ordinary API defects separate from deliberately vulnerable training endpoints. Never call a 500 response an authorization bypass without observing unauthorized access or mutation. Initialization has its own bounded deadline; epoch budgets and between-call token thresholds do not impose a hard money cap.
